## The problem retries create

A client POSTs to `/payments`. Your server processes the charge. The response is lost on the way back — a timeout, a dropped connection, a load balancer with an itchy trigger.

The client has no way to distinguish "the request never arrived" from "it succeeded and the response was lost." So it retries. And the customer is charged twice.

This is not an edge case. It is the ordinary behaviour of networks, and any API that moves money must be built for it. The mechanism is an **idempotency key**: a client-supplied identifier that lets the server recognise a retry and return the original result instead of doing the work again.

## Where the key comes from

The key must be generated by the **client**, and it must identify the *intent*, not the attempt.

```javascript
// Correct: one key per user intent, reused across retries
const idempotencyKey = crypto.randomUUID();

async function pay(order) {
  return withRetries(() =>
    fetch('/api/payments', {
      method: 'POST',
      headers: { 'Idempotency-Key': idempotencyKey },   // same key each retry
      body: JSON.stringify(order),
    })
  );
}
```

Generating a fresh key inside the retry loop defeats the entire mechanism — each attempt looks like a new payment. This is the most common implementation error, and it is invisible until a customer is double-charged.

Server-generated keys cannot work either: the server would have to return the key in the response, and the failure you are protecting against is precisely the response not arriving.

If a natural business identifier already uniquely identifies the intent — an order ID, a USSD session ID, an M-PESA transaction ID — use it. Fewer moving parts, and it survives a client that forgets to send a header.

## The naive implementation and its race

The obvious approach:

```python
# Has a race window
def create_payment(key, payload):
    existing = IdempotencyRecord.query.filter_by(key=key).first()
    if existing:
        return existing.response

    result = charge_card(payload)
    IdempotencyRecord.create(key=key, response=result)
    return result
```

Between the `SELECT` and the `INSERT` there is a window. Two retries arriving simultaneously — which is exactly what an impatient client or a load balancer retry produces — both find nothing, both charge the card.

The window is small. It is also hit routinely in production, because retries cluster rather than arriving randomly.

## Insert first, let the database arbitrate

The fix is to claim the key *before* doing the work, and let a unique constraint resolve the race:

```sql
CREATE TABLE idempotency_records (
    key           VARCHAR(64) PRIMARY KEY,
    request_hash  CHAR(64)    NOT NULL,
    state         VARCHAR(16) NOT NULL,   -- IN_PROGRESS | COMPLETE
    response_code INT,
    response_body JSON,
    created_at    TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    locked_until  TIMESTAMP
);
```

```python
def create_payment(key, payload):
    request_hash = sha256_of(payload)

    try:
        with db.session.begin():
            db.session.add(IdempotencyRecord(
                key=key, request_hash=request_hash,
                state="IN_PROGRESS",
                locked_until=utcnow() + timedelta(seconds=90),
            ))
            db.session.flush()          # raises here if the key exists
    except IntegrityError:
        return handle_existing(key, request_hash)

    # We own this key. Do the work exactly once.
    result = charge_card(payload)

    record = IdempotencyRecord.query.get(key)
    record.state = "COMPLETE"
    record.response_code = 201
    record.response_body = result
    db.session.commit()
    return result, 201
```

The `PRIMARY KEY` is doing the real work. Exactly one concurrent request wins the insert; every other gets an `IntegrityError` and takes the existing-record path. No application-level locking, no race.

## Handling the three states of an existing key

```python
def handle_existing(key, request_hash):
    record = IdempotencyRecord.query.get(key)

    # 1. Same key, different payload — a client bug, not a retry
    if record.request_hash != request_hash:
        abort(422, "Idempotency-Key reused with a different request body")

    # 2. Still running — tell the client to wait, do not duplicate
    if record.state == "IN_PROGRESS":
        if record.locked_until > utcnow():
            return {"error": "Request in progress"}, 409
        record.state = "FAILED_STALE"      # worker died mid-flight
        db.session.commit()
        abort(503, "Previous attempt did not complete; retry with a new key")

    # 3. Complete — replay the original response verbatim
    return record.response_body, record.response_code
```

Each branch matters.

**The request-hash check** catches a real bug class: a client reusing a key across genuinely different payments. Without it, request B silently returns request A's result and the second payment never happens. Failing loudly is far better.

**The `IN_PROGRESS` branch** is what most implementations omit. A retry arriving while the original is still charging must not proceed — `409 Conflict` tells the client to back off and retry shortly.

**`locked_until`** handles the worker that dies mid-charge. Without an expiry, that key is poisoned forever and the customer can never complete the payment.

**Replaying the stored response** — including the original status code — is the entire point. The client gets byte-identical results whether it called once or five times.

## What to store, and for how long

Store the response *body and status*, not just a success flag. The client may need the payment ID or receipt number from the original response.

Do not store the full request body — it contains card details, phone numbers, amounts. A SHA-256 hash is enough to detect key reuse without retaining sensitive data.

Retention of 24–72 hours is typical. Long enough that any plausible client retry — including a mobile app resuming after a long offline period — still matches. Expire with a scheduled cleanup; an unbounded table becomes its own problem.

## Which operations need this

Not every endpoint does. The test is whether the operation is naturally idempotent:

| Operation | Needs a key? | Why |
|---|---|---|
| `GET /payments/123` | No | Reads change nothing |
| `PUT /users/5` (full replace) | No | Same result applied twice |
| `DELETE /payments/123` | No | Already-deleted is already the goal |
| `POST /payments` | **Yes** | Creates a new charge each time |
| `POST /transfers` | **Yes** | Moves money each time |
| `POST /sms/send` | **Yes** | Sends a message each time |

`POST` that creates a resource with side effects is the case that needs protection. Note the pattern: operations that *set* state are naturally safe; operations that *change state by a delta* are not.

## Receiving webhooks is the same problem, reversed

Everything above assumes you are the server. When you receive webhooks from Paystack, Stripe or M-PESA, you are the client of someone else's at-least-once delivery — and the same mechanism applies with their event ID as the key.

The rule that matters there: **write the idempotency record inside the same transaction as the business logic.** Two separate transactions leave a window where the event is marked processed but the work never committed, which is the worst of the three possible outcomes.

## In short

Retries are guaranteed; exactly-once is something you build. Have the client generate one key per intent and reuse it across attempts. Claim the key with a unique constraint before doing any work. Handle in-progress retries explicitly rather than letting them through. Replay the stored response verbatim.

None of this is difficult. It is just easy to skip until the first duplicate charge, which tends to be an expensive way to learn it.
